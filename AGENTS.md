# AGENTS.md

Ты работаешь над внутренней системой управления FBS-заказами и мебельным производством для Ozon.

Полное продуктовое ТЗ находится в:

`/docs/PRODUCT.md`

Текущее состояние проекта находится в:

`/docs/STATE.md`

Конкретные задачи находятся в:

`/tasks/`

---

# 1. Главное правило работы

НЕ перечитывай весь репозиторий перед каждой задачей.

Для выполнения задачи используй минимально необходимый контекст:

1. `/AGENTS.md`
2. `/docs/STATE.md`
3. текущий файл задачи из `/tasks/`
4. только связанные с задачей исходные файлы
5. нужные разделы документации

`PRODUCT.md` является главным полным ТЗ, но не нужно перечитывать его полностью для каждой маленькой задачи.

Если текущая задача содержит достаточно информации — работай по ней.

# 2. Главная бизнес-цель

Система должна заменить бумажное управление производством.

Работник цеха должен открыть телефон и сразу понять:

# 5. Важное правило Ozon

Никогда не смешивать:

**Ozon Status**

и

**Internal Production Status**

Это две разные сущности.

Ozon показывает логистическое состояние отправления.

Internal Production Status показывает состояние заказа внутри нашего мебельного производства.

---

# 6. Работа с Ozon API

Не придумывать:

- endpoints;
- поля;
- форматы webhook;
- ограничения API.

Если задача связана с Ozon API и есть хоть малейшее сомнение — сначала проверить актуальную официальную документацию Ozon Seller API.

Не использовать deprecated endpoints, если существуют актуальные.

Предпочтительная схема:

Ozon Webhook
→ Backend
→ Database
→ realtime update приложения

Дополнительно:

Scheduler
→ Ozon API
→ reconciliation

Reconciliation нужен как страховка от:

- потерянного webhook;
- временной недоступности;
- ошибок обработки;
- изменения данных без ожидаемого события.

Webhook должен быть идемпотентным.

Повторное событие не должно создавать дубликаты.

# 7. Priority Engine

Priority Engine является одной из главных частей проекта.

Приоритет заказа должен учитывать:

- время до shipment deadline;
- время до shipment_date_without_delay;
- следующую ступень тарификации;
- финансовый эффект;
- стоимость заказа;
- ориентировочное время производства;
- наличие blocker;
- ручной priority override;
- возможность физически закончить заказ вовремя.

Приоритет должен быть объяснимым.

Недостаточно показать:

`Priority score: 84`

Нужно показывать причины.

Например:

**КРИТИЧЕСКИЙ**

Причины:

- тариф ухудшится через 1 ч 20 мин;
- потенциальный финансовый эффект: 640 ₽;
- производство занимает около 45 минут.

---

# 8. Money at Risk

Money at Risk — обязательная функция.

Dashboard руководителя должен показывать потенциальный финансовый риск по времени.

Пример:

Деньги под угрозой: 11 480 ₽

До 12:00:
1 840 ₽

До 16:00:
ещё 3 120 ₽

До конца дня:
ещё 6 520 ₽

Каждая сумма должна быть кликабельной.

После нажатия пользователь должен видеть конкретные заказы, из которых она складывается.

Дополнительно разделять:

- можно успеть;
- высокий риск;
- заблокированные;
- уже произошедшее ухудшение.

Нельзя придумывать денежную сумму, если её невозможно корректно вычислить из данных Ozon.

Все денежные вычисления выполнять через Decimal.

Не использовать float для денег.

# 9. Problems → Manager Tasks

Любая производственная проблема не должна оставаться просто комментарием.

Если работник создаёт blocker:

1. создаётся Blocker;
2. заказ при необходимости переходит в BLOCKED;
3. автоматически создаётся Manager Task;
4. руководитель получает уведомление.

Manager Task должен содержать минимум:

- id;
- source_type;
- source_id;
- order/posting;
- title;
- description;
- severity;
- status;
- assigned_to;
- created_at;
- due_at;
- resolved_at.

Не создавать несколько одинаковых активных Manager Tasks для одной причины.

После устранения причины Manager Task должен автоматически закрываться там, где это логично.

---

# 10. Manager Tasks могут создаваться автоматически

Manager Task может возникать не только из blocker.

Автоматически создавать задачи при:

- критическом blocker;
- дорогом заказе с приближающимся дедлайном;
- просрочке;
- заказе без ответственного;
- заказе, который слишком долго находится в одном статусе;
- просроченной закупке;
- отмене Ozon после начала производства;
- ошибке Ozon sync;
- проблеме webhook;
- заканчивающемся Ozon API key.

Не создавать spam.

Нужны правила дедупликации.

# 13. Security

Обязательные правила:

- HTTPS;
- безопасное хранение паролей;
- Argon2id или актуальный безопасный аналог;
- API keys только backend;
- secrets не хранить в git;
- secrets не логировать;
- Ozon API Key никогда не отправлять frontend;
- HttpOnly cookies для auth, если используется cookie auth;
- rate limit login;
- input validation;
- upload size limits;
- MIME validation;
- RBAC backend enforcement;
- audit logging.

Не хранить долгоживущие auth tokens в localStorage.

---

# 14. Database

Для денег использовать:

Decimal / PostgreSQL NUMERIC.

Все timestamps хранить в UTC.

Timezone организации является настройкой.

Создавать необходимые indexes.

Не делать N+1 запросы без необходимости.

Использовать pagination.

# 25. Главный принцип продукта

Система создаётся не ради красивого dashboard.

Она должна реально ускорять мебельное производство.

Каждая функция должна отвечать хотя бы на один вопрос:

- что делать сейчас;
- что горит;
- где проблема;
- кто отвечает;
- сколько денег можно потерять;
- что готово к отгрузке.

Если функция не помогает производству или управлению — не усложнять MVP без необходимости.
