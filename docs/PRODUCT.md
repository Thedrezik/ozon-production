Ты — senior full-stack developer, system architect и DevOps engineer.

Твоя задача — СПРОЕКТИРОВАТЬ И РЕАЛИЗОВАТЬ с нуля production-ready систему управления заказами и производством для продавца мебели на Ozon по схеме FBS.

Это не задача на написание концепта или псевдокода. Нужно создать реально работающий проект, который можно развернуть на VPS.

==================================================
1. БИЗНЕС-КОНТЕКСТ
==================================================

Сейчас процесс выглядит так:

1. На Ozon приходит FBS-заказ.
2. Владелец утром вручную открывает Ozon Seller.
3. Печатает заказы на бумаге.
4. Бумажные листы передаются в мебельный цех.
5. Работники вручную ставят галочки.
6. Комментарии вроде:
   - произведено;
   - не хватает кромочной ленты;
   - нужна фурнитура;
   - готово к упаковке;
   - готово к отгрузке
   пишутся от руки.
7. Нельзя нормально понять:
   - какой заказ наиболее срочный;
   - какой заказ выгоднее отгрузить сегодня;
   - сколько денег будет потеряно при задержке;
   - где именно завис заказ;
   - кто им занимается;
   - каких материалов не хватает.

Нужно полностью перевести этот процесс в цифровой вид.

2. ГЛАВНАЯ ЦЕЛЬ
==================================================

Создать мобильную production-management систему, которая:

- автоматически получает FBS-заказы Ozon;
- мгновенно показывает новые заказы;
- сама строит очередь производства;
- показывает дедлайн отгрузки;
- показывает текущую тарификацию Ozon;
- показывает следующую тарификацию;
- рассчитывает финансовый эффект ранней или поздней отгрузки;
- показывает таймер до ухудшения тарифа;
- автоматически рассчитывает приоритет заказа;
- позволяет отслеживать внутреннее состояние производства;
- позволяет назначать ответственных;
- позволяет оставлять комментарии;
- позволяет создавать проблемы/блокеры;
- позволяет отмечать нехватку материалов;

- отправляет уведомления;
- имеет пользователей, роли и детальные права доступа;
- хранит полную историю действий.

Основная цель интерфейса:

работник цеха должен открыть телефон и сразу понять:

==================================================
4. OZON SELLER API
==================================================

Перед реализацией интеграции обязательно открой и изучи АКТУАЛЬНУЮ официальную документацию Ozon Seller API.

Не копируй слепо старые примеры из GitHub или StackOverflow.

По состоянию на постановку задачи основным методом списка FBS является:

POST /v4/posting/fbs/list

Но перед реализацией ещё раз проверь официальный API.

Используй push/webhook-уведомления Ozon там, где это возможно.

Также обязательно сделай периодическую reconciliation-синхронизацию как страховку от пропущенного webhook.

Пример архитектуры:

Ozon
 ↓
Webhook
 ↓
FastAPI
 ↓
PostgreSQL
 ↓
WebSocket/SSE
 ↓
PWA

Плюс:

scheduler
 ↓
Ozon API
 ↓
сверка данных

Ориентировочно делать reconciliation каждые 3–5 минут.

Интервал вынести в настройки.

Webhook должен обрабатываться идемпотентно.

Повторное получение одного события не должно создавать дубликаты.

Перед реализацией webhook обязательно проверить в документации:
- формат payload;
- способы проверки webhook;
- подтверждение endpoint;
- retries;
- доступные event types;
- требования Ozon по HTTP status;
- ограничения API.

Не придумывать механизм подписи webhook, если его нет в документации.

==================================================
7. PRIORITY ENGINE
==================================================

Это один из главных компонентов.

Нельзя просто сортировать заказы по времени создания.

Создай Priority Engine.

Он должен учитывать:

1. Просрочен ли заказ.
2. Время до shipment_date_without_delay.
3. Время до shipment_date.
4. Время до следующей ступени тарификации.
5. Финансовую разницу между тарифами.
6. Стоимость заказа.
7. Примерное время производства.
8. Внутренний ручной приоритет.
9. Наличие блокера.
10. Возможность физически закончить заказ до дедлайна.

Priority Engine должен быть ПРОЗРАЧНЫМ.

На карточке заказа должно быть написано не просто:

Priority = 83.

А:

"КРИТИЧЕСКИЙ"

Причины:
- тариф изменится через 1 ч 42 мин;
- потенциальная потеря 640 ₽;
- производство занимает ~50 минут.

Сделать уровни:

P0 — Критический
P1 — Срочный
P2 — Сегодня
P3 — Плановый
P4 — Можно позже

Администратор должен иметь возможность менять параметры алгоритма.

Например:

- critical_hours;
- urgent_hours;
- today_hours;
- вес финансовой потери;
- вес времени;
- ручной приоритет.

Должна быть возможность PIN / "Поднять в очереди".

Ручное изменение приоритета обязательно фиксировать в audit log.

Заказы с блокером отображать отдельно:

"Срочные, но заблокированные".

68. ФИНАЛЬНОЕ ТРЕБОВАНИЕ

8. Система должна продолжать работать даже при временной недоступности Ozon.
9. Она должна быть достаточно лёгкой для VPS 1 CPU / 1 GB RAM.
10. Код должен быть простым, поддерживаемым и готовым к дальнейшему расширению.
